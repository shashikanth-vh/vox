RBAC — Final Architecture & Call Flows

Spec ATLAS_RBAC_v3.1.xlsx Shape Gateway + Access service + Register Tests 77 passing — incl. 7 e2e on the real 3-service stack (CF1–CF7)
Three services, three jobs:
· ACCESS owns the facts — users, roles, access-matrix tables, editable by Admin only, no deploy needed.
· GATEWAY (REST-API service) decides binary (NONE / FULL) in-process from cached facts — and hosts future client-specific logic.
· REGISTER decides SCOPED next to the data, re-verifies binary, and runs the operation — the final authority.
01 · Architecture

The request path, top to bottom

The Access service sits beside the request path, not on it — the gateway pulls facts from it and caches them (refreshed by TTL or on change), so no request ever waits on a "may I?" network call. Only the scoped question travels to the data, because only the data can answer it.

02 · The decision ladder

Every request resolves in at most two steps

NONE → 403
decided at the GATEWAY · no data touched

BDRM calls reassign lead · Management calls delete. Cached matrix settles it in-process — the request never crosses into the data plane.

FULL → pass
decided at the GATEWAY · Register re-verifies

Credit Head edits any lending line. Gateway forwards with role headers; Register's re-check is a dict lookup, then the operation runs.

SCOPED → ask the data
decided at the REGISTER, next to the row

Deal Analyst edits a syndication line — allowed only if an active line_assignments row ties them to that line. Revoked the moment the assignment ends.

03 · Call flows

Eight flows cover every case

CF1

First request of a session — facts get cached, menu renders

The only time the Access service is on the path — and only until the cache is warm. Afterwards, thousands of requests decide from memory.

sequenceDiagram
  autonumber
  participant U as ATLAS UI
  participant G as Gateway
  participant AC as Access service
  participant R as Register
  U->>G: GET /v1/me  (X-User-Email)
  G->>AC: /resolve?user=… (cache miss)
  AC-->>G: roles + compiled matrix + version → cached (TTL ~60s)
  G->>R: forward with X-User-Roles
  R-->>U: views{} · operations{} · active assignments[]
  Note over U: menu & buttons drawn from this — cosmetic only
CF2

Binary DENY — stopped at the gateway

Spec: “Delete a row — Admin ONLY.” Management is denied at the gate from cache — zero network calls, the Register never sees the request.

sequenceDiagram
  autonumber
  participant M as Management user
  participant G as Gateway
  participant R as Register
  M->>G: DELETE /v1/entities/{id}
  G->>G: cache: matrix[delete_row][Management] = NONE
  G-->>M: 403 forbidden (RFC-9457)
  Note over R: never reached
CF3

Binary ALLOW — FULL access, straight through

Gateway decides FULL from cache and forwards; the Register's re-verify is one dict lookup, then the write runs with locking + history + audit in one transaction.

sequenceDiagram
  autonumber
  participant C as Credit Head
  participant G as Gateway
  participant R as Register
  participant P as PostgreSQL
  C->>G: PATCH /v1/lending/{id} (If-Match: v)
  G->>G: cache: matrix[edit_lending_line][Credit Head] = FULL
  G->>R: forward + X-User-Email, X-User-Roles
  R->>R: re-verify binary (dict lookup) ✓
  R->>P: optimistic-lock update · history · audit — one txn
  R-->>C: 200 + new ETag
CF4

SCOPED — the Register answers the residual question

The assignment-driven primitive. Same user, same operation: assigned line → 200, any other line → 403. Ending the assignment revokes instantly.

sequenceDiagram
  autonumber
  participant A as Deal Analyst
  participant G as Gateway
  participant R as Register
  participant P as PostgreSQL
  A->>G: PATCH /v1/syndication/{lineX}
  G->>G: cache: SCOPED → forward, flag scope
  G->>R: forward + role headers
  R->>P: SELECT 1 FROM line_assignments WHERE user, Syndication, lineX, active
  alt assigned to lineX
    R->>P: apply update · history · audit
    R-->>A: 200
  else not assigned
    R-->>A: 403 — not your line
  end
CF5

Admin edits access — live in seconds, no deploy

Why the matrix is tables, not code: an Admin-role user changes a grant in the Access service; the version bump invalidates gateway caches. Guardrail cells refuse the edit.

sequenceDiagram
  autonumber
  participant Ad as Admin user
  participant AC as Access service
  participant G as Gateway
  Ad->>AC: PATCH /v1/access {operation, role, grant}
  AC->>AC: Admin-only check · guardrail check (immutable cells refuse) · audit the change
  AC-->>Ad: 200 · matrix version++
  G->>AC: next /resolve (TTL expiry or version poke)
  AC-->>G: new matrix → cache refreshed
  Note over G: new rules enforced platform-wide within seconds
CF6

Request → approve — routed to the right vertical, applied atomically

Stays in the Register: approval must apply the stage change, append history and audit in ONE transaction with the tracker row.

sequenceDiagram
  autonumber
  participant An as Deal Analyst
  participant R as Register (via gateway)
  participant AH as AM Head (wrong vertical)
  participant CH as Credit Head (right vertical)
  An->>R: POST /v1/requests {Lending line, stage → "Note Circulated"}
  R-->>An: 201 Pending (from_value stamped)
  AH->>R: POST /v1/requests/{id}/approve
  R-->>AH: 403 — AM Head may not decide Lending
  CH->>R: POST /v1/requests/{id}/approve
  R->>R: apply stage · history {from,to,at,by} · audit — one txn
  R-->>CH: 200 Approved · re-decide later → 409
CF7

Bypass attempt — why the Register re-verifies

An internal caller (worker, script, misrouted service) reaches the Register without passing the gateway. Defense in depth catches it — the vault defends itself.

sequenceDiagram
  autonumber
  participant W as Internal caller (skips gateway)
  participant R as Register
  W->>R: DELETE /v1/deals/{id}  (X-User-Email: mgmt@…)
  R->>R: re-verify: matrix[delete_row][Management] = NONE
  R-->>W: 403 — same wall, different door
  Note over R: no user header → REGISTER_ENFORCE_RBAC governs (trusted-system mode off/on)
CF8

Future — client-specific logic lives in the gateway only

The reason the REST-API service exists as its own deployable: per-client adaptations land here and nowhere else. Core services never fork per client.
