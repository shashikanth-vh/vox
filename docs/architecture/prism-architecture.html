01 · System architecture

One entry point, one source of truth, one database server

Every request enters through NGINX, passes the Gateway's cached binary RBAC gate, and lands on the Register — the platform's source of truth, which enforces scoped access next to the data. Identity & the admin-editable access matrix live in the Access service; document bytes live in MinIO/S3; Temporal drives durable workflows. One PostgreSQL server, a database per service.

03 · Functionality flows

Every functionality, end to end

Thirteen flows, F1–F13. Each shows the exact path a request takes through the system as built.

F1

Request pipeline — under every API call

The common spine: edge controls, then auth → tenant → row-level-security scope, so a query can never cross tenants even if a filter is forgotten.

sequenceDiagram
  autonumber
  participant C as Client
  participant N as NGINX
  participant G as Gateway
  participant A as Register API
  participant P as PostgreSQL
  C->>N: request + X-API-Key, X-Tenant, X-User-Email
  N->>G: proxy · rate-limit · mint X-Request-ID
  G->>G: binary RBAC gate from cache — NONE → 403 here
  G->>A: forward + secret-stamped identity + X-Authz-Decision
  A->>A: API-key check → tenant lookup → verify gateway secret
  A->>P: SET app.current_tenant (RLS) · scoped check if needed
  P-->>A: rows
  A-->>C: JSON + ETag · errors as RFC-9457 problems
F2

Create a record — idempotent

One surface for all 16 tables. A retried POST with the same Idempotency-Key replays the stored outcome instead of creating a duplicate.

POST /v1/<resource> · header Idempotency-Key

flowchart LR
  A["POST + Idempotency-Key"] --> B{"key seen before?"}
  B -- yes --> C["replay stored response
Idempotency-Replay: true"]
  B -- no --> D["INSERT row (version = 1)"]
  D --> E["audit_log entry"]
  E --> F["store key → response (48 h TTL)"]
  F --> G["201 + ETag"]
F3

Update / delete — optimistic locking

No lost updates: every row carries a version; a stale write gets 409 and re-reads. Deadlocks and serialization failures retry server-side with backoff. Deletes are soft and restorable.

PATCH /v1/<resource>/{id} · DELETE … · POST …/restore · header If-Match

flowchart LR
  A["PATCH + If-Match: v"] --> B{"version matches?"}
  B -- no --> X["409 version_conflict
re-read and retry"]
  B -- yes --> C["apply changed fields only"]
  C --> D["stage/status changed?
auto-append {from,to,at,by} history"]
  D --> E["version++ · audit_log"]
  E --> F["200 + new ETag"]
  A -.deadlock 40P01 / serialization 40001.-> R["server-side retry, backoff + jitter"] -.-> A
F4

List — keyset pagination, filters, search

Stable O(1)-at-depth pagination on (created_at, id) — no page drift at lakhs of rows. Whitelisted equality filters; trigram-backed search.

GET /v1/<resource>?q=&limit=&cursor=&with_total=

flowchart LR
  A["GET list"] --> B["tenant + not-deleted"]
  B --> C["+ whitelisted filters
?sector= · ?status= · …"]
  C --> D["+ q → ILIKE across searchable columns"]
  D --> E{"cursor?"}
  E -- yes --> F["WHERE (created_at,id) < cursor"]
  E -- no --> G["first page"]
  F --> H["fetch limit+1 → items + next_cursor"]
  G --> H
F5

Document upload — bytes to MinIO/S3, row to the catalog

Multipart upload against any record — lead, deal, lending, syndication, asset-mon, entity, counterparty. The subject is validated before the upload, so no orphan objects. With no object store configured, small files (≤ 400 KB) fall back inline — the ATLAS rule.

POST /v1/<subject>/{id}/documents/upload · POST /v1/documents/upload · POST /v1/documents (reference-only)

F9

Financials — append-only versioning

Audited-March vs restated-June never overwrite each other. An advisory lock serialises writers per statement; exactly one version stays is_current.

POST /v1/financials · GET /v1/financials/history

sequenceDiagram
  autonumber
  participant C as Client
  participant A as Register API
  participant P as PostgreSQL
  C->>A: new statement (entity, type, period, data)
  A->>P: pg_advisory_xact_lock(entity, type, period)
  A->>P: max(version_no) → n
  A->>P: UPDATE old versions is_current = false
  A->>P: INSERT version_no = n+1, is_current = true
  A-->>C: 201 — history preserved, one current

F12

Durable workflow — exactly-once effect

The platform pattern for multi-step operations: orchestration in Temporal, all I/O in activities via the SDK. The idempotency key derives from the workflow id, so Temporal's retries can never double-write the Register.

worker services/workflows · task queue prism-workflows

F14

RBAC — the three-service enforcement (summary)

Binary decisions at the Gateway from cached facts; SCOPED decided by the Register next to line_assignments; the matrix is admin-editable data in the Access service — a grant change is live platform-wide in seconds, no deploy. Full detail (decision ladder + CF1–CF8): the companion RBAC — Architecture & Call Flows page.

flowchart LR
  A["request + X-User-Email"] --> B{"gateway: matrix[op][roles]
(cached from Access /resolve)"}
  B -- NONE --> X["403 at the gateway"]
  B -- FULL --> C["forward: X-Authz-Decision FULL"]
  B -- SCOPED --> D["forward: X-Authz-Decision SCOPED"]
  C --> R["Register: run the operation"]
  D --> E{"assigned to THIS line?"}
  E -- yes --> R
  E -- no --> Y["403 — not your line"]
